# Official MCP C# client SDK fit for Urd

**Research-only recommendation (2026-11-04).** The official C# SDK is a sensible default for MCP client protocol and transport mechanics. I found no evidence-based reason to reject it. This is not a dependency selection or an architecture decision: Urd's model interface, loop, storage, process/session topology, and dynamic-discovery exposure remain open. No package was installed and no MCP server was contacted.

## Verdict

Start any later implementation comparison with the single package **`ModelContextProtocol.Core` 2.3.1**, the SDK's minimum-dependency client/low-level package, rather than hand-writing JSON-RPC, transports, OAuth protocol plumbing, and protocol-version compatibility. The exact published package is new (NuGet lists it on 2026-11-03); pinning this version is a research anchor, not a commitment. Verify the release and target MCP server matrix in an offline/controlled integration test before adopting it.

Two qualifications matter, but neither is a blocker:

1. Core has a **mandatory `Microsoft.Extensions.AI.Abstractions` dependency** and exposes MCP tools as `AIFunction`. That does **not** force Urd to adopt `IChatClient`, full `Microsoft.Extensions.AI`, or its optional model/tool loop. If avoiding even the abstractions package is a requirement, this SDK does not meet it; no such requirement is recorded.
2. The latest protocol revision (2026-07-28) is materially different from the previous handshake/session revisions. The SDK supports dual-era compatibility, but server/transport interoperability is not established by Urd's current probes. In this revision, list-change events require an explicit `subscriptions/listen`; SDK 2.3.1 has the protocol DTOs and low-level request/notification APIs but no typed client convenience API for that subscription. A small adapter or direct low-level call may be needed if Urd chooses live list-change tracking. Initial listing and calls do not require it.

Most importantly, **SDK MCP discovery is not model exposure**. It lists remote server tool definitions and invokes remote tools. Urd must independently decide which definitions enter its tool catalog/model request, how they fit its pruning and cache-prefix policies, and how a model call is authorized, routed, and recorded. No model library, wrapper, or discovery policy is implied here.

## Protocol is versioned, with optional capabilities—not a frozen feature checklist

MCP standardizes JSON-RPC messages, transport bindings, version rules and feature contracts, but the dated specification revisions evolve. The previous `2025-11-25` revision and earlier use `initialize` to negotiate a protocol version and capabilities for a session. `2026-07-28` removes that handshake and HTTP session model: requests carry version/capability metadata, servers implement `server/discover`, and clients can probe then select a mutually supported revision. A peer need not implement every optional feature. Capabilities/extensions and particular tools/resources/prompts are conditional; Urd need not implement sampling, elicitation, roots, resources, prompts, logging, tasks, or other advanced features to start with a tools-only client.

SDK 2.3.1's default prefers `2026-07-28`, probes `server/discover`, then falls back to the older `initialize` handshake when appropriate; explicitly setting `ProtocolVersion` pins the request and disables downgrade below it. HTTP transport defaults to auto-detection: try Streamable HTTP, then legacy SSE. Don't confuse protocol revision fallback with HTTP transport detection. `2026-07-28` Streamable HTTP is stateless (no session ID/resume); earlier Streamable HTTP revisions support stateful sessions/resumption. The SDK's `ResumeSessionAsync` applies only when the selected server/transport actually has a resumable session; it is not generic replay/recovery.

For tools, the specification defines `tools/list`, `tools/call`, JSON Schema definitions, structured or heterogeneous content results, `isError`, and protocol errors. Listing supports cursor pagination and caching hints. In SDK 2.3.1, `ListToolsAsync()` aggregates pages but performs **no internal list cache**; the lower-level page API exposes the response/caching hints. Earlier revisions used a `tools.listChanged` capability and notifications; the current revision requires clients to opt into `subscriptions/listen` for change notifications. The SDK source includes that protocol's request/notification types, but no convenience client method to open/manage a tools-list subscription was found. If Urd wants live updates, verify and wrap the low-level API rather than assuming a handler registration alone subscribes. It is also acceptable to defer subscriptions and refresh on reconnect or at an explicit Urd lifecycle point.

**Concurrency and recovery:** the client session correlates concurrent in-flight JSON-RPC requests, but that does not guarantee a particular MCP server's tools are safe to run concurrently or that side effects are idempotent. Urd owns admission/serialization policy. Under the current 2026 revision, MCP requests are sessionless; older Streamable HTTP revisions have session IDs and an explicit resumption path. Stdio process restart loses in-flight requests. On any transport, a lost response does not establish whether a side effect occurred. The SDK's cancellation/reconnect support is not an exactly-once or safe-replay guarantee; do not retry an uncertain tool call automatically.

## Caveats ranked by relevance

1. **MEAI abstractions in the dependency graph — definite, bounded impact.** Core directly depends on `Microsoft.Extensions.AI.Abstractions` (plus `Microsoft.Extensions.Logging.Abstractions`); `McpClientTool` inherits `AIFunction`. The full `Microsoft.Extensions.AI` middleware, `IChatClient`, provider adapters, and `FunctionInvokingChatClient` are not required by the MCP SDK. Thus the dependency is not a reason to couple MCP calls to Urd's model loop. Check the dependency graph against Urd's eventual .NET target before selection.
2. **Server/transport/version matrix — qualification gap, not SDK blocker.** The 2026 revision is very recent; server support will vary. Source/docs demonstrate fallback paths, not successful interoperability with Urd's chosen servers. Test at least a modern Streamable HTTP server, stdio, and any required legacy server/HTTP+SSE endpoint. Do not force an old revision unless compatibility evidence requires it.
3. **App-owned lifecycle and credentials — normal glue.** Disposal owns stdio process cleanup; it is not tied to each tool call. Urd's backend must keep clients alive independently of a browser request and agent/session lifetimes. Default stdio environment inheritance can pass model/API credentials into child processes; configure it deliberately. HTTP OAuth callback and durable token persistence are Urd responsibilities if needed. These are boundaries the SDK makes configurable, not missing protocol support.
4. **Live dynamic list-change convenience — narrow gap.** If Urd needs to react immediately to changes on `2026-07-28` servers, client glue around `subscriptions/listen` is indicated. It does not block initial tool listing/calling or require Urd to adopt MCP subscriptions before its discovery behavior is chosen.
5. **Packaging and license — manageable checks.** The package targets .NET 8/9/10 and .NET Standard 2.0; the SDK itself is managed NuGet code, not a cross-platform-native MCP server bundle. A stdio server's language runtime/executable remains an external configured prerequisite; Urd's .NET self-contained publish would not automatically bundle it. The package build metadata declares Apache-2.0; the repository license describes a transition where unrelicensed original contributions remain MIT and non-spec docs are CC-BY-4.0. Preserve package license/notice information and check the exact package manifest and transitive notices if distributing. No incompatibility with Urd's current license was established here.

## Minimal sensible scope, pending choices, acceptance

A first integration can stay deliberately small: configure one stdio and/or Streamable HTTP server; connect/dispose it at backend-owned lifetime; negotiate versions; list tools with pagination; preserve definitions/results/errors; make tools available only through Urd's separately controlled model/discovery path; invoke them with Urd's chosen cancellation and permission rules. Defer OAuth unless a protected remote server is a selected use case; defer change subscriptions unless dynamic updates require them. This is not a process-topology or model-interface recommendation.

**Still open:** supported server/transport matrix and .NET target; per-server environment policy; OAuth UX and secure token cache; Urd representation/permission/exposure of MCP tools; whether/list-change subscription behavior; concurrency limits, reconnect and uncertain-call policy. None is a reason to write a replacement MCP wire stack.

**Focused acceptance scenarios (offline fixtures first):**

1. Start a fake local stdio server, list paginated definitions, call one with arguments, distinguish a tool `isError` result from an RPC exception, then dispose and verify clean bounded process exit. Verify cancelling one request does not stop the server process.
2. Connect to a fake modern Streamable HTTP peer and a legacy initialize-based peer; confirm the negotiated protocol version and compatible tool list/call path. If legacy SSE is in scope, explicitly cover it instead of assuming the HTTP happy path proves fallback.
3. Return mixed text/image and structured content plus metadata; verify Urd's chosen path preserves the complete `CallToolResult` and call/result error distinction rather than accidentally flattening it.
4. Exercise a paginated tools list and, only if selected, a current-revision `subscriptions/listen` change event; ensure it causes an explicit re-list/update, not implicit model exposure. Confirm lack of optional notification capability still permits ordinary list/call.
5. Simulate transport loss after a side-effecting call is sent but before its result arrives; confirm the call is marked uncertain and not blindly replayed. For OAuth, use a local fake auth endpoint and verify callback/token-cache behavior without using provider accounts.
