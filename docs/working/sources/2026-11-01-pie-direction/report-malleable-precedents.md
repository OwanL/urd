# Source-first vs runtime-extensible: precedents and lessons for Pie

## Bottom line

- **Source-first customization does work, but only when the code users edit is small.** Examples are dwm (~2k lines), kickstart.nvim (one file), shadcn/ui (leaf components) and NanoClaw (a small core). Pie plus its Pi fork is about 400k non-test lines. Asking every user to keep a fork of that up to date is the VS Code fork problem (Cursor, VSCodium), not the dwm situation.
- **Every source-first project that survives updates ends up adding seams anyway.** Examples include dwm's `config.h`, NanoClaw's skills with tests at each touch point, Backstage and React Native upgrade diffs, `shadcn diff`, and LazyVim turning the distribution into a dependency. So "go source-first and delete the extension machinery" is only half right. You can delete runtime *loading*, but you still have to design and keep stable *boundaries*.
- **Pie is already running this experiment, and the result so far is bad.** It vendored Pi v0.80.6 and changed 98 files (+18k lines). Pi upstream has since released 1.0.0 (Oct 1) through 1.4.0 (Oct 21), roughly weekly (from `npm view`). I found no resync commits in `harness/pi`. If the maintainer, who has full context, isn't reconciling with upstream, users with a 400k-line Pie fork won't either.
- **Do not build a GUI plugin API.** This is the most expensive kind of extension surface to keep stable. It would be built on a 6-month-old UI that still changes constantly, for one maintainer, with no demonstrated demand.
- **Evolve in place by replacing parts gradually (strangler pattern), not with a fresh repo.** The brief bundles two separate decisions. The rewrite question is about complexity and fatigue, not about the customization model.

## Precedents

| Precedent | How customizations survive updates | Ecosystem effect | Cost to maintainer | Failure mode |
|---|---|---|---|---|
| **suckless dwm/st** | User keeps a git branch of patches and rebases it on master ([dwm: patches in git](https://dwm.suckless.org/customisation/patches_in_git/)). Wiki patches are pinned to versions and conflict with each other. | Patches are shared on a wiki but not composable; heavy forks stop pulling upstream ([r/suckless](https://www.reddit.com/r/suckless/comments/y407qn/updating_dwm_after_drastic_changes/)). | Close to zero. Upstream is tiny, rarely changes, and ignores downstream. | Only works because the core is ~2k lines of rarely changing C and users are self-selected enthusiasts. |
| **Emacs** | Everything is reachable at runtime, so internals effectively become the API. | Huge, long-lived ecosystem. | Internals are frozen by users' dependence on them. | "Emacs bankruptcy": configs grow until people start over; packages break silently ([tuxes.uk](https://b.tuxes.uk/avoiding-emacs-bankruptcy.html), [Irreal](https://irreal.org/blog/?p=13105)). |
| **Neovim: kickstart vs LazyVim** | kickstart: a template you own; "use this template", or fork if you want upstream sync ([README](https://github.com/nvim-lua/kickstart.nvim)). In practice it is rarely updated. LazyVim: the starter *imports LazyVim as a plugin* and users add overrides in `lua/plugins/` ([LazyVim plugins](https://lazyvim.github.io/configuration/plugins), [starter](https://github.com/LazyVim/starter/blob/main/lua/config/lazy.lua)). | Both depend on Neovim's stable Lua plugin API and its large plugin ecosystem. | kickstart stays deliberately tiny. | The "you own it" model gives up updates. Users wanting updates move to the dependency-plus-overrides model. |
| **shadcn/ui** | Copied code with no versions and no alerts: "the component in your repository is exactly as good as the day you installed it" ([21st.dev](https://21st.dev/blog/keeping-copied-components-updated)). Diffing is an experimental `shadcn diff` ([changelog](https://v3.shadcn.com/docs/changelog)). Long-standing request for merge support ([#376](https://github.com/shadcn/ui/issues/376)). | Adoption exploded because units are small, leaf-level and stable. | Low, because update responsibility moves to users. | Bug and security fixes don't reach users. Works only for leaf code that nothing else depends on. |
| **Omarchy (dotfiles distro)** | Refreshing configs overwrites user edits and keeps a `.bak` ([#5821](https://github.com/basecamp/omarchy/issues/5821), [#8063](https://github.com/omacom/omarchy/discussions/8063)). DHH's lock-and-diff idea: "you then have to manually merge things in. That feels grating." It was closed as not planned ([#619](https://github.com/basecamp/omarchy/issues/619)). | Strong opinionated defaults drive adoption. | Ongoing support churn. | User-owned copies of defaults that keep evolving cannot also receive the new defaults. Keep defaults and overrides in separate layers. |
| **VS Code forks (Cursor, VSCodium)** | Cursor's fork diff reportedly exceeded 350k added lines and lagged upstream 1.93 vs 1.96 ([r/cursor](https://www.reddit.com/r/cursor/comments/1i6tors/how_do_they_rebase_their_fork_of_vscode/)). Users reported "dozens of tiny papercuts" ([Cursor forum](https://forum.cursor.com/t/vs-fork-question/5105)). | Forks lose the marketplace. Microsoft's C/C++ extension stopped working in forks in April 2025 ([The Register](https://www.theregister.com/software/2025/04/24/microsoft-subtracts-c/c-extension-from-vs-code-forks/721912), [EclipseSource](https://eclipsesource.com/blogs/2024/12/17/is-it-a-good-idea-to-fork-vs-code/)). | Needs a dedicated, funded team. | Lag, papercuts and lost ecosystem access. This is the realistic picture of "every user keeps a Pie fork". |
| **Obsidian** | Stable plugin API; plugins upgrade separately from the app. | 4,000+ plugins and themes, 120M+ downloads ([Obsidian blog](https://obsidian.md/blog/future-of-plugins/)). Plugins are central to adoption. | High: review, security, and a new directory/dashboard. Plugin maintenance is a known problem ([arXiv 2602.17018](https://arxiv.org/html/2602.17018)). | Abandoned plugins and supply-chain risk. |
| **Home Assistant** | Formal deprecation policy with minimum periods, because custom integrations use internals ([deprecating](https://contributors.home-assistant.io/core/development/deprecating/)). | Custom integrations are a big part of its value. | Every internal change needs a deprecation cycle. | Integrations that import private classes break anyway, e.g. xtend_tuya in 2026.1 ([#694](https://github.com/azerty9971/xtend_tuya/issues/694)). |
| **Firefox XUL → WebExtensions** | XUL add-ons reached all internals. Mozilla replaced this with a narrow, stable API. | The rich XUL ecosystem died, and well-known add-ons were lost ([How-To Geek](https://www.howtogeek.com/333230/why-firefox-had-to-kill-your-favorite-extension/)). | "If there was an XPCOM component used by add-ons, it simply could not be changed in incompatible ways… a nightmare for Firefox developers" ([Yoric](https://yoric.github.io/post/why-did-mozilla-remove-xul-addons/)). | Exposing internals produces a "development tax" on the core and a "maintenance tax" on extension authors. **This is exactly what source-first becomes if users' edits depend on internals.** |
| **Grafana / Backstage** | Grafana took multiple major versions (v9 to v12) to retire Angular plugins ([Grafana](https://grafana.com/blog/angularjs-support-will-be-removed-in-grafana-12-what-you-need-to-know/)). Backstage's new frontend system is a multi-year migration with documentation gaps ([#34134](https://github.com/backstage/backstage/issues/34134), [#31294](https://github.com/backstage/backstage/issues/31294)). Backstage apps are also source you own, updated with template diffs ([upgrade-helper](https://github.com/backstage/upgrade-helper)), the same approach as React Native ([rn-diff-purge](https://github.com/react-native-community/rn-diff-purge)). | Plugins are the product. | UI plugin APIs cost *years* to change. | GUI extension points become permanent. Source-you-own needs dedicated diff tooling. |
| **NanoClaw (agent-maintained fork)** | "Once you edit the code, every upstream update turns into a merge fight." Fix: "every change you make is a skill". Changes should be additive, with "a test for each spot where it touches the rest of the system". Update with `/update-nanoclaw` ("Don't just git pull"): it stages in a worktree, runs test gates, snapshots state and supports rollback. "Changes edited directly into the core are the one thing the model can't protect." ([customizing.md](https://github.com/nanocoai/nanoclaw/blob/HEAD/docs/customizing.md), [no features](https://nanoclaw.dev/blog/nanoclaw-has-no-features/)) | Skills replace features. Sharing happens at the skill level. | Maintainer promises "every breaking change ships with its migration". | **The closest precedent to Pie's idea, and it rebuilt an extension contract** (additive modules + contract tests + update tool). |
| **Ink & Switch, "Malleable software" (2025)** | n/a | Plugins "can only edit an app's behavior in specific authorized ways". "AI code generation alone does not address all the barriers." "Bringing AI coding tools into today's software ecosystem is like bringing a talented sous chef to a food court." You need a *kitchen*. Design for a "gentle slope", where each step up in power needs only a small extra investment ([essay](https://www.inkandswitch.com/essay/malleable-software/), [Litt 2023](https://www.geoffreylitt.com/2023/03/25/llm-end-user-programming.html)). | | Going from config straight to "edit 400k lines" is a cliff, not a slope. |
| **Pi itself** | A minimal core plus "Pi can create extensions. Ask it to build one" ([pi.dev](https://pi.dev/docs/latest/extensions), [Zechner](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/), [Ronacher](https://lucumr.pocoo.org/2026/1/31/pi/)). | Third-party Pi packages, which Pie already uses (`pi-mcp-adapter`, `pi-web-access`). | A small core keeps it manageable. | Pi is already "agent writes the customization" with a *runtime* seam. That is the strongest argument against removing it. |

## Rewrite vs evolve

- Spolsky: Netscape's from-scratch rewrite cost about three years with no releases. Old code holds hard-won bug fixes, and "these problems can be solved, one at a time, by carefully moving code, refactoring" ([Joel](https://www.joelonsoftware.com/2000/04/06/things-you-should-never-do-part-i/)).
- Counterexamples: Basecamp 2 and 3 were successful rewrites, but the old versions **kept running** and nobody was forced to migrate ([SvN](https://signalvnoise.com/posts/3856-the-big-rewrite-revisited), [Tsai's 6 stories](https://mjtsai.com/blog/2019/02/19/lessons-from-6-software-rewrite-stories/)). The common view now is that big-bang cutovers are the problem, not rewriting itself ([HN](https://news.ycombinator.com/item?id=23725867)). The incremental "strangler fig" approach of replacing parts gradually is the standard alternative ([Fowler](https://www.martinfowler.com/bliki/StranglerFigApplication.html)). One weak, single-source figure: across 41 programs, 76% of strangler projects completed vs 50% of big-bang rewrites ([artofcto](https://theartofcto.com/guides/rewrite-vs-refactor-decision-framework)).
- What AI changes: writing code is now cheap. *Rediscovering edge cases* is not. Pie's 1,450 commits are mostly durability, recovery, Windows and lifecycle fixes, the exact knowledge Spolsky says a rewrite throws away. A fresh repo that ports pieces is just a strangler migration with an extra repo boundary, while the maintainer keeps two codebases alive.

## Conclusions for Pie

**1. Pure source-first does not hold up at Pie's current size.** Every precedent where it works has a tiny core or tiny units. At about 400k lines with daily churn, each user's fork turns into a Cursor-style lag-and-papercut problem. "The agent will rebase it" is unproven. Pie's own Pi fork, about four upstream releases behind with no resync, is the evidence. **Test it first:** have an agent rebase `harness/pi` onto Pi 1.4.0 and measure the time and breakage. If that is painful for you, it will be worse for users.

**2. Removing runtime customization machinery is mostly the wrong cut.**
- *Data* layers are cheap and are where cross-tool sharing already happens: instructions, skills, agents, MCP config, provider config. Keep them as separate layers, not copied defaults (Omarchy's lesson).
- Pi's tool/extension seam brings in an outside ecosystem at no cost. Keep it.
- What to cut instead: unused layering variants, Pie-specific plugin APIs, and any planned GUI extension API.

**3. Use a hybrid with a gentle slope (option D), with source-first as the top step, not the only one:** config → skills/agents → Pi tools/extensions → source edits. For source edits to be practical, all of these must be true:
- **Small, named seams.** Registries for tools, panels/views, providers and commands, so user code is *additive* (new files plus one registration line), never in-place edits to core files.
- **Contract tests per seam** that user customizations reuse (the NanoClaw model).
- **An update tool:** `pie update` / an update skill that rebases in a scratch branch, runs the seam tests, and can roll back. Never a raw `git pull`.
- **A migration note** whenever a seam breaks. Treat seams as a semver'd API. The Firefox lesson: whatever users touch, you're stuck maintaining.
- **A one-command, fast source build on Windows.** The 318 MB immutable-generation VSIX is the opposite of a modify-and-rebuild loop.
- **A smaller core.** Without it, none of the above stays cheap.

**4. Don't build UI extension points.** Grafana, Backstage and Firefox show that GUI plugin APIs cost years to change. For the rare user who wants a custom panel, "add a file under `panels/` and register it" (an internal seam, agent-written) gives 90% of the value at a fraction of the cost.

**5. Evolve in place.** Pick the *requirements* to drop first (that is where the complexity comes from), then delete and carve seams with the strangler pattern while keeping the product shippable. A fresh repo only makes sense if the old one is frozen and the new core is very small, and even then it would regrow the same complexity unless requirements are cut. Bluntly: if the real motivation is "this codebase is too big for me and my agents to hold in their heads," that is an argument for **cutting scope**, not for changing repos or customization model.
