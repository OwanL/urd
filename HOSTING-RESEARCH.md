# C#/.NET HTTP hosting research

**Research date:** 2026-11-03. **Subsequent decision: ASP.NET Core/Kestrel selected.** The owner accepted the hosting choice after this investigation; see [ARCHITECTURE.md](ARCHITECTURE.md#aspnet-core-hosting-and-http). The comparison below is research history, not an open hosting selection. Minimal APIs remain a recommendation; .NET version, process topology, access/authentication and packaging remain open.

## Recommendation for the next qualification step

Use **ASP.NET Core on Kestrel with Minimal APIs** as the baseline to evaluate first, without adding MVC or a third-party endpoint layer unless a concrete requirement earns it. This is a recommendation for a low-cost comparison baseline, **not an approved implementation choice**. Microsoft recommends Minimal APIs for new projects, citing simpler syntax, less boilerplate, easier testing and better performance; those are Microsoft's general claims, not Urd measurements. Kestrel is the standard cross-platform ASP.NET Core server. This path provides routing, middleware, streamed responses, server-sent events (SSE), WebSockets and in-process hosted services without introducing a separate HTTP server dependency. [Microsoft: API choices](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/apis?view=aspnetcore-10.0) · [Kestrel](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel?view=aspnetcore-10.0) · [Minimal API responses](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis/responses?view=aspnetcore-10.0) · [Hosted services](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/host/hosted-services?view=aspnetcore-10.0)

**Support-policy caveat, not a demonstrated functional blocker:** Microsoft's Kestrel guidance says macOS is supported for development, CI and local services *without external access*, but not production server workloads. This does not establish that Kestrel prevents LAN/Tailscale connections. The owner explicitly does not treat the vendor support boundary as a selection blocker; working Urd behaviour is the criterion. Normal macOS functional testing remains necessary, and no such test was performed here. The initial report overstated the policy note's significance.

### What the baseline buys, and what it does not establish

- Minimal APIs cover ordinary HTTP endpoints and the documented streaming/SSE/WebSocket paths. Microsoft lists controllers mainly for model-binding extensibility, advanced MVC validation, application parts/application-model features and OData. .NET 10 adds Minimal API validation; endpoint filters cover cross-cutting handler logic. **Inference:** these controller-specific features are not currently evident in Urd's source-editable, single-user backend, so MVC controllers would add a convention and pipeline without a demonstrated need. Revisit if actual requirements call for those features. [Validation and Minimal APIs](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis?view=aspnetcore-10.0) · [Endpoint filters](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis/min-api-filters?view=aspnetcore-10.0)
- `BackgroundService`/`IHostedService` are intended for long-running work and can run in a web host. This fits a shared backend that continues agent work after a UI disconnects, but Urd must keep agent lifetimes separate from request-abort cancellation. Graceful shutdown is not crash recovery; the docs note shutdown callbacks may not run after abrupt process failure. [Hosted services](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/host/hosted-services?view=aspnetcore-10.0)
- ASP.NET Core ships as the `Microsoft.AspNetCore.App` shared framework, rather than requiring individual ASP.NET Core framework assemblies as NuGet packages. ASP.NET Core is MIT-licensed; this review identified no license friction, but is not a legal review. [Shared framework](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/target-aspnetcore?view=aspnetcore-10.0) · [License](https://github.com/dotnet/aspnetcore/blob/main/LICENSE.txt)
- Kestrel can host directly or behind a reverse proxy. Its docs cover request/time limits and other safeguards, but explicitly say it is not the primary DDoS defense. LAN/Tailscale binding, TLS, remote-client authentication and browser trust need a deliberate design; the Linux development-certificate workflow is not as turnkey as Windows/macOS. No access-control or TLS design is selected here.
- Microsoft calls Kestrel lightweight and suitable for resource-constrained environments. **That is not a Urd performance result.** No comparable app-level CPU, memory, startup, LOC or sustained-fan-out measurements were found or run.

## Credible alternatives

These are actual alternative HTTP server stacks, unlike endpoint-routing libraries below. Their existence and feature lists do not prove a Urd advantage.

| Option | Evidence and possible benefit | Limits / qualification |
| --- | --- | --- |
| **Watson Webserver** | Standalone server using its own `TcpListener`/`QuicListener` paths rather than Kestrel; project documents HTTP/1.1, HTTP/2, optional HTTP/3, WebSockets and streaming/SSE. Current project targets .NET 8/10; MIT. [Repository](https://github.com/dotnet/WatsonWebserver) · [project file](https://github.com/dotnet/WatsonWebserver/blob/main/src/WatsonWebserver/WatsonWebserver.csproj) · [license](https://github.com/dotnet/WatsonWebserver/blob/main/LICENSE.md) | Promising only if it demonstrates a concrete capability or materially lower total cost. Its performance figures are project-reported and environment-sensitive; the README itself says Kestrel remains ahead. No independent matched benchmark, Urd integration/build, or verified Windows/macOS/Linux support matrix. Do not infer lower overhead from its transport implementation. |
| **TouchSocket HTTP** | A separate networking stack with an HTTP/1.1 server/client, WebSockets and large-file transfer; Apache-2.0 for `TouchSocket.*`. [Repository](https://github.com/RRQM/TouchSocket) · [license](https://github.com/RRQM/TouchSocket/blob/master/LICENSE) | Broader networking framework (multiple transports/protocols, plugins, related packages) than Urd's apparent HTTP need. Project throughput claims are not independent comparisons. SSE fit, cross-OS deployment and source-build burden remain unverified. |
| **`HttpListener`** | Built into .NET. [API documentation](https://learn.microsoft.com/en-us/dotnet/api/system.net.httplistener?view=net-10.0) | Microsoft discourages it for new development and documents narrower Linux/macOS support, including no HTTPS there. Not a sound cross-platform shortcut for Urd. |
| **HTTP.sys** | ASP.NET Core server with Windows-specific kernel-mode features such as port sharing and Windows authentication. [ASP.NET Core server comparison](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers?view=aspnetcore-10.0) | Windows-only; Microsoft recommends Kestrel unless HTTP.sys-specific features are needed. It conflicts with Urd's planned macOS/Linux rollout as a shared server choice. |

No alternative has demonstrated a benefit large enough to justify replacing the standard baseline. Only pursue a prototype if a specific macOS support constraint, required protocol, measured resource target or other need makes Kestrel unsuitable.

## Thin API layers are not server alternatives

These run **on ASP.NET Core/Kestrel**; they do not replace the HTTP server. They mainly trade added dependencies/conventions for endpoint organization.

- **FastEndpoints** is an MIT ASP.NET Core endpoint/REPR layer (current package research: 8.3.0; targets .NET 8/9/10). It provides endpoint classes/discovery and validation helpers, among other features. [Repository and license](https://github.com/FastEndpoints/FastEndpoints) · [NuGet package](https://www.nuget.org/packages/FastEndpoints/8.3.0). It may help if its handler structure proves substantially clearer for Urd, but there is no evidence yet that it reduces total maintained code compared with direct Minimal APIs.
- **Carter** is an MIT, deliberately thin layer over ASP.NET Core Minimal APIs, organizing routes into modules; current package research: 10.0.0, targeting .NET 10. [Repository](https://github.com/CarterCommunity/Carter) · [NuGet package](https://www.nuget.org/packages/Carter/10.0.0). Its scope appears small, but it still adds a package and convention. No demonstrated requirement presently calls for it.
- **ServiceStack** is an ASP.NET Core application framework, not an alternate server. Its proprietary product terms include free-use quotas and runtime license enforcement; the vendor lists a free cap of 10 operations, and its free open-source license-key allowlist does not name Urd's AGPL-3.0. A backend's final endpoint count is not designed yet, but this limit and licensing ambiguity make it a poor fit absent written clarification and a viable user-local-build model. [Terms](https://servicestack.net/terms) · [free-use terms](https://servicestack.net/free) · [pricing](https://servicestack.net/pricing) · [Urd license](LICENSE). This is a fit warning, not legal advice.

None of these layers has been built or compared for Urd. Adding one should be justified by actual endpoint code and maintenance cost, not by the assumption that a framework is inherently better structured.

## Source builds and release costs

Editing and locally rebuilding source is an agreed product requirement; a prebuilt release alone does not satisfy it. A user changing C# source needs the matching .NET SDK and dependency restore. ASP.NET Core's shared framework is installed with the SDK/runtime. Framework-dependent publishing is the default and requires the ASP.NET Core runtime on the target machine; self-contained publishing bundles the runtime but is per OS/architecture and does not automatically roll forward runtime security patches. Single-file publishing is also platform-specific. [Deployment modes](https://learn.microsoft.com/en-us/dotnet/core/deploying/) · [Runtime support policy](https://learn.microsoft.com/en-us/dotnet/core/releases-and-support)

For qualification, compare a normal JIT build first. Native AOT is optional, adds platform-specific native-build and compatibility constraints, and is not a prerequisite for local source editing. Microsoft's compatibility table marks MVC unsupported for Native AOT and Minimal APIs partially supported. No release, clean-machine source build, or packaging rehearsal was performed in this research; the project's existing C# probe is not such evidence. [Native AOT](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/native-aot?view=aspnetcore-10.0)

## Still open; not decided by this research

- Supported OS/version matrix and functional verification of Urd's intended macOS LAN/Tailscale access. The owner has accepted the vendor support-policy caveat.
- HTTP endpoint/event shape, TLS and remote-client authentication; background/tray process topology and UI-disconnect behavior.
- .NET target version, endpoint style, whether any API layer earns its dependency, and framework-dependent versus self-contained release packaging.
- Actual whole-process resource use, sustained agent fan-out, startup, and build/test experience on Windows, macOS and Linux. None was benchmarked or qualified here.

**Evidence limits:** This was primary-source documentation/repository research, not an implementation trial. Project benchmark/throughput statements above are vendor claims, not comparable measurements. Cross-platform target frameworks and source links are not proof of every-OS runtime support. The prior [Go/.NET discovery](GO-DOTNET-DISCOVERY.md) likewise did not test HTTP servers or establish app-level resource or packaging results.
